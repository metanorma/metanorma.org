== Commenter 0.4–0.6: the complete ISO ballot workflow

Two days ago we https://www.metanorma.org/blog/2026-08-27-commenter-0.3-osd-redline-github/[introduced commenter 0.3]: ISO comment intake from the DOCX balloting template, ISO Online Standards Development (OSD) XLSX exports, and ISO/CS editor redlines — all into one schema-validated YAML. That work was done for the ISO 2533 publication; this follow-up trio of releases (0.4.0, 0.5.0, 0.6.0) finishes the job: the whole ballot lifecycle now runs on that one YAML file.

[source,shell]
----
gem install commenter
----

== Collation: merge member-body sheets

A secretariat receives one comment file per member body per ballot — and late redlines by email. ISO's own Comment Collation Tool gives up on non-conforming formatting, so merging happens by hand. Now:

[source,shell]
----
commenter merge de.yaml us.yaml jp.yaml cs-redline.yaml -o ballot.yaml
----

Metadata comes from the first sheet that provides each field, identical duplicates are dropped, and a comment ID carrying different content in two files stops the merge loudly instead of silently losing someone's comment.

== Resolution on GitHub: a real sync

`github-create` has always made one issue per comment. Working groups that resolve comments as GitHub issues needed more than create-once: `github-sync` treats the YAML as the source of truth and reconciles the issues with it.

[source,shell]
----
commenter github-sync --config github_config.yaml ballot.yaml
----

Missing issues are created; issue content is refreshed from the YAML under a configurable conflict policy (`--conflict yaml`, `github`, or `skip` — because which side wins is situational); and an open issue whose comment has a recorded disposition is closed, which is exactly what keeps the observation round-trip working. Stage-aware unique IDs (`[DIS] GB-001`) ensure the same comment number at CD and DIS gets its own issue.

== Reporting: statistics and stage comparison

Ballot reports need disposition counts, and until now every standards body we looked at — OASIS resolution logs, W3C disposition-of-comments documents, ISO ballot summaries — counted them by hand. The data is already in the YAML:

[source,shell]
----
commenter stats ballot.yaml
----

The same comment ID reappears at every ballot stage, so comparing two stages answers the working group's standing question — what happened between CD and DIS:

[source,shell]
----
commenter diff cd-ballot.yaml dis-ballot.yaml
----

New, withdrawn, repeated, revised, and resolved counts, as a Markdown table that pastes straight into WG minutes.

== Export: the final deliverable in one command

The ballot's last step used to be two: pull the observations the WG recorded in issue comments, then fill the comment sheet template. Now:

[source,shell]
----
commenter export ballot.yaml --config github_config.yaml -o disposition.docx --shading
----

Closed-issue observations are retrieved, the template is filled with the sheet's Date/Document/Project header metadata, and disposition cells get status-based shading (accepted, accepted-with-modifications, noted, rejected).

== Under the hood

The data model now serializes through https://github.com/lutaml/lutaml-model[lutaml-model] — the same foundation Metanorma uses elsewhere — with typed nested models for comment locality and GitHub tracking state. Short type codes (`ge`/`te`/`ed`) are normalized on load, the disposition vocabulary lives in one matcher shared by shading and statistics, and the suite has grown from 38 to 122 examples with CI green across Ruby 3.2–4.0 on macOS, Linux, and Windows.

Comments, bug reports, and pull requests are welcome at https://github.com/metanorma/commenter[github.com/metanorma/commenter] — and if a format you receive isn't handled yet, a sanitized sample file is the fastest way to get it supported.
